# Architectural Decision Records (ADR)

This document records the foundational architectural decisions and the technical opinions defended in the Team of Six (TOS) project.

| title | context | decision | consequence |
| :--- | :--- | :--- | :--- |
| **Trimodal Team Architecture** | Standard AI coding tools grant LLMs direct file access, leading to cognitive collapse and security risks. | Split the development cycle into three functional personas: **Architect** (Wisdom/Review), **Agent** (Reasoning), and **Ghost** (Execution). | High-integrity development; the Architect performs PR-style reviews and test execution in a local environment before merging Ghost mutations. |
| **The Contextual Trinity** | LLMs lose reasoning accuracy when the task surface is too broad or the context window is cluttered with irrelevant history. | Structurally enforce a **1:1:1 mandate**: exactly one Issue, one Branch, and one Feature per workspace. | Physical isolation of work that eliminates scope drift and ensures the Agent is grounded in a specific, narrow logic. |
| **Ephemeral Outbox Grounding** | LLMs suffer from "prompt drift" when relying on chat memory and lose track of the actual repository state. | Reject long-term chat history; regenerate a verified context document (the Outbox) directly from Git on every workspace transition. | Every turn starts in a "Clean Room" snapshot, forcing the Agent to derive logic from the current "Remote Truth" of the repo. |
| **Plaintext IPC Protocol** | Structured formats like JSON or YAML frequently cause parser failures due to LLM syntax errors (nested brackets, escaping). | Use a flat, plaintext protocol utilising uppercase markers (e.g., `===TOS_FILE_START===`) for Inter-Process Communication. | Dramatic increase in generation reliability; the Ghost parses blocks via simple AWK, and the Agent saves tokens for reasoning. |
| **Isolated Ghost Sandbox** | Executing AI-generated commands in a human's local environment risks data loss, credential theft, or environment pollution. | All file mutations occur in a restricted Unix user sandbox (`${TOS_MNT_ROOT}/sandbox/`) isolated from the Architect's home directory. | The Architect's local environment remains the "clean" space for verification; AI work is treated as an external contribution. |
| **HITL Micro-Protocol** | LLMs often "rush to code," skipping critical reasoning steps and resulting in syntax-heavy hallucinations. | Enforce a 4-step cognitive cadence in the Agent rulefile: **Mirror**, **Challenge**, **Plan**, then **Execute**. | The Architect validates the Work Breakdown Structure (WBS) before code is written, ensuring lead-level oversight of junior-level execution. |
| **Shell-Centric Engine** | Compiled languages or heavy frameworks add overhead and opacity, making it difficult to audit AI-triggered actions. | Implement the gateway and core logic modules using **Zsh** scripts and standard Unix tools only. | The framework is lightweight, audit-friendly, and natively composes with standard Git and GitHub CLI tools. |
| **Lock Hierarchy** | Writing to the filesystem during brainstorming or planning phases causes state corruption and unnecessary I/O. | Segregate work phases via atomic locks: **Soft Lock** (Trinity 0) for planning and **Hard Lock** (Trinity N) for code mutation. The lock tier is encoded by the physical directory placement (`soft/` vs `hard/`) of each action script — the gateway requires no hardcoded action lists. | Mechanically prevents the Agent from committing code during ideation until the Architect explicitly transitions to a feature Trinity. |
| **The Locked Manifest (Intent Locking)** | Post-hoc MANIFEST checks at closure time verify what the Agent *did*, but not whether it was *authorised* to do it. Any file within the sandbox is technically reachable by a `write code` payload. | The Agent must declare its exact file scope in a `write plan` payload, which writes an approved `.manifest` visa to the control plane before `write code` is permitted. The gateway cross-references every file in a `write code` payload against this visa before writing a single byte. | Mechanically blocks the Agent from successfully writing to any file outside its upfront-approved scope. Rogue file hallucinations are rejected at the gateway before they reach the sandbox. |
| **Exact-Once Execution (Inbox Truncation Invariant)** | If an operation fails mid-execution and the inbox is preserved, retrying causes duplicate side effects (double commits, double issue creation). | Truncate the inbox to zero bytes immediately after parsing, before any filesystem or network side effects occur. | Guarantees exact-once execution semantics. If a command fails after truncation, the payload is deliberately lost and the Architect must manually resubmit. This is a feature, not a bug. |
| **Out-of-Band Recovery Doctrine** | Automated self-healing in the sandbox (e.g., auto-rebasing on a push rejection) violates the physical isolation barrier and creates unauditable state changes. | On any critical failure (e.g., `git push` rejection during the Atomic Handover), the system halts immediately and logs the full error to the Outbox. It makes no attempt to resolve, rebase, or self-heal. | The system's state is always recoverable by the Architect via explicit out-of-band commands (`close trinity`, manual remote resolution). The Ghost never silently changes state. |
| **HITL Destructive Gate (CONFIRM=TRUE)** | An Agent operating on a stale or confused context could hallucinate a destructive `close` or `delete` command, wiping project history or sandbox state. | Require the exact string `CONFIRM=TRUE` in the `TOS_META` payload for any `close` or `delete` operation. The gateway aborts before executing any logic if this string is absent. | Creates a hard mechanical safety net ensuring explicit human intent before any finality or purge operation executes. |
| **PAT MFA Isolation** | A fully-scoped GitHub token resident in the sandbox could allow a compromised or hallucinating Ghost to permanently delete remote repositories without human intervention. | The Ghost's base Personal Access Token must lack `delete_repo` scope. Repository deletion requires an interactive OAuth browser escalation (`gh auth refresh -s delete_repo`) that cannot be performed non-interactively via `sudo -n`. The elevated scope is revoked immediately after use via a registered `EXIT` trap. | True out-of-band Multi-Factor Authentication for the nuclear `delete project` command. The remote truth cannot be destroyed by an automated process alone. |
| **Pre-Escalation Caller Verification** | The gateway escalated to the Ghost in Stage 1 and only then verified the Architect's working directory in Stage 3b. That check ran `git remote get-url origin` as `team_of_six`, inside the Architect's tree — the Ghost reading the Architect's filesystem, which the entire sandbox model exists to forbid. Because the failure was swallowed by `\|\| true`, any directory the Ghost could not traverse (a `0700` home, a `mktemp -d`, an encrypted home mount) reported as "not a git repository" and sent the Architect to `create project` for a repository that already existed. | All caller-location verification happens in **Stage 0, before the `sudo` escalation**, performed by the Architect against their own filesystem. **No module and no gateway stage running as the Ghost may read any path outside `${TOS_MNT_ROOT}`.** A guard on `id -un` makes the block inert on the re-exec. | Sandbox isolation is restored as a mechanical property rather than an aspiration: the Architect's working tree is unreadable to the Ghost, and a non-traversable project directory is now simply irrelevant instead of producing a misleading diagnostic. Any future check that needs to know where the Architect is standing must live in Stage 0. |
| **The Phase Gate** | TOS makes explicit what the Agent may see, touch and do, but not where it stands in the Red-Green-Refactor-Retrospect cycle. The phase is not derivable from the repository: green and refactor are indistinguishable, since a refactor changes implementation without changing behaviour and leaves no artifact. An Agent asked to know its phase is therefore guessing over an unbounded set — the exact failure the framework exists to prevent. Separately, `write trinity` merges without consulting review state, leaving the one step that reaches `main` unguarded. | Store an explicit phase per Trinity in a Ghost-exclusive `.phase` file beside the lock, initialised to red by `create trinity`. The phase moves only when the Architect submits a review carrying a transition tag naming both endpoints — `[PHASE:GREEN->REFACTOR]` with `--approve` — and runs `tos <project> write phase`; where several tagged reviews have accumulated, the latest wins. The gate is forward-only: a transition advances exactly one step and never retreats or skips, because `close trinity` restores the pre-Trinity state and is the exit from a wrong phase. Every read re-derives the whole record from GitHub with no fast path: the review must resolve on the current PR, its source must equal the current phase, its verdict must be APPROVED, it must be chronologically later than the last transition, its commit must be an ancestor of HEAD, and its author must not be the Ghost. GitHub is authoritative — on disagreement the command refuses and never silently repairs. `write trinity` refuses unless the phase is retrospect, checked before the MANIFEST audit; `sync trinity` reports `PHASE=` in the snapshot; `close trinity` is the sole command that does not validate, making abandonment the recovery path for a corrupted record. | The Agent is told its phase rather than selecting one, closing the last axis on which it was permitted to guess. Skipping the Retrospective becomes mechanically impossible and the Architect's approvals become load-bearing. Costs a fifth control-plane artifact, a new command, three forward reviews per Trinity, and an API call on every sync. A corrupted record costs the Trinity — deliberately: a record thrashed badly enough to lock it is evidence the Trinity was scoped too large, and the enforced restart reports something true about the work. Branch protection on `main` remains necessary independently — it is the only guarantee that survives a compromised gateway, and this gate is layered above it rather than replacing it. |
